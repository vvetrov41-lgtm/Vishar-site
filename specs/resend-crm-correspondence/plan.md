## Risk
Resend generates its own RFC Message-ID; a receipt UUID is not a thread ID. The current Gmail scopes are read-only and send, not import/modify. Gmail's external send-as feature is being retired in January 2027, so a new dependency on that feature is not a durable solution.

## Verified production SQL findings
Read-only inspection of live RPC definitions: claim_email_outbox leases approved_email with SKIP LOCKED and joins only enabled Google email integrations. service_resolve_gmail_outbox_target rechecks current lease, recipient, lifecycle and booking authority. record_email_outbox_result currently hard-codes google_gmail, including activity metadata; it must not record a Resend receipt as Gmail. service_record_review_email_sent requires Gmail thread and RFC identifiers. Introduce a separate durable provider attempt and explicit receipt path before wiring. Resend's July 8 2026 release exposes actual RFC Message-ID in signed webhooks and retrieve/list endpoints (https://resend.com/changelog/message-id-for-sent-emails); use signed webhook reconciliation, not an invented ID. API idempotency lasts 24 hours (https://resend.com/docs/api-reference/emails/send-email); adapter uses a conservative 23h deadline based on a persisted attempt. The initial adapter only accepts the owner's exact test address and is not wired into any worker endpoint or drain. No API key is configured in the production Gmail Worker as of this inspection. Consider an authenticated mailbox copy for Gmail-visible history only after validating recipient-count quota and correlation; do not enable it by default.
