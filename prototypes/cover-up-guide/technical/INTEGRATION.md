# Lead Magnet Foundation — review candidate

Production audit: no lead-magnet tables on 27 Nov 2026. `client_marketing_consent` is client-scoped; `email_messages` and the approved-email Gmail worker are tied to client/enquiry or existing approved automation. Using them unchanged would create fake client records or bypass approval. The existing book waitlist is Telegram-only and doesn't persist a recipient. Do not reuse it as a lead capture.

## What is implemented here
- `lead-magnet-intake.mjs`: isolated API boundary, default off. Validates origin, strict fields, bounded body, email, honeypot, rate-limit binding, explicit marketing opt-in and stable request UUID. Refuses attribution until the consent adapter is implemented. Server response must confirm durable database queue before front end reports success. Inject `capture` with the service-only RPC (not accessible from the browser). `node --test lead-magnet-intake.test.mjs` runs five unit tests with a mock backend.
- `lead-magnet-foundation.sql`: SQL review candidate for private artist-scoped magnets, contacts, enrolments, requests, and delivery jobs; dedupe by request and per version/step. No actual DB migrations applied. Server-derived artist slug for pilot; other artists require explicit independent route binding and tenant verification. New tables RLS enabled and direct grants revoked. No existing CRM rows touched. Unsubscribe RPC disables marketing across enrolments for one artist/contact; requires HTTPS confirmation endpoint. No direct write from public UI. SQL has not been executed against Postgres; do not treat it as a released migration.
- Landing preview (`../landing/index.html`): production endpoint is planned, not live; form preview never sends POST. `data-mode=live` may only be changed after full integration, including delivery, consent, privacy notice, asset publication and E2E checks.
