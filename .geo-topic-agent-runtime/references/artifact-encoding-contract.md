# Artifact Encoding Contract

All user-facing and machine-readable artifacts generated by this runtime must preserve Unicode text exactly.

## Required Encoding

- Markdown, JSON, JSONL, TXT, and generated HTML reports: UTF-8.
- CSV artifacts: UTF-8 with BOM (`utf-8-sig`) for safer Windows/Excel opening; readers must accept UTF-8 with or without BOM.
- Generated HTML reports must include `<meta charset="utf-8">` in `<head>`.
- JSON must be written with `ensure_ascii=False` so Cyrillic stays readable.

## Mandatory Writers

Runtime tools must write artifacts through `geo_topic_agent.core` writers:

- `write_text`
- `write_json`
- `write_csv`
- `write_html_report` or `build_html_document` plus `write_text`

Do not create user-facing artifacts with shell redirection, PowerShell `Set-Content`, `Out-File`, ad-hoc browser snippets, or text replacement that can silently use console code pages. If a one-off HTML dashboard is needed, generate it through `write_html_report` or include an equivalent UTF-8 preflight and post-write verification.

## Windows Process Boundary

- Set `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8`, and use `python -X utf8` when invoking runtime scripts on Windows.
- Never pipe a PowerShell here-string that contains non-ASCII user data directly into `python -`; the host console/code page may replace characters before Python sees them.
- Pass Russian queries through a UTF-8 file read by `read_text_lossless`, a UTF-8 environment/argument boundary, or an ASCII-only script that reconstructs required literals with Unicode escapes.
- Runtime subprocesses must capture bytes (`text=False`) and decode with `decode_text_bytes`; no child-process output may use a system-default text codec or `errors=ignore`.
- A subprocess timeout is a failed/blocked observation. Terminate the child, preserve bounded stdout/stderr bytes and do not mark the stage complete.

## Guardrails

The writer contract rejects generated artifacts when it sees signs of irreversible encoding damage. Internal guard label: `question_mark_loss`.

- repeated question marks such as `????` where Cyrillic labels should be;
- common UTF-8/Windows mojibake;
- generated HTML without an explicit charset.

`geo_agent/data/raw/` and `geo_agent/data/import/` are evidence zones. They may preserve provider/user bytes as received, but normalized reports, processed CSVs, source inventories, and summaries must pass the encoding guard.

## Recovery Rule

If an artifact contains `????`, do not manually translate the damaged labels in place. Treat the artifact as corrupted, go back to the source rows/JSON/text, regenerate with UTF-8 writers, then verify the regenerated file.

## Verification

Before telling the user that a Russian dashboard/report is ready:

1. Read the file as UTF-8 bytes.
2. Confirm the expected Russian control words are present, for example `Видимость`, `Цитирование`, `Запрос`, `Бренд`, `Ошибка` when those labels are used.
3. Confirm there is no `????`, replacement character, or mojibake in the generated report or source inventory.
4. For HTML, confirm `<meta charset="utf-8">` exists before opening the file in a browser.

If a terminal or UI displays mojibake but the file passes UTF-8 byte verification, report it as a display/codepage issue instead of rewriting the artifact.
