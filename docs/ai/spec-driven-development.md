# Spec-driven development in Vishar-site

This repository uses a Vishar-adapted Spec Kit workflow for substantial product and architecture work.

Upstream reference: `github/spec-kit` v1.0.0.

The integration intentionally uses the Spec Kit artifact model and skill names while keeping Vishar-specific branch, CI, security, migration, and deployment governance authoritative.

## Why this exists

Long-lived Vishar CRM work often spans database migrations, Workers, private CRM UI, provider integrations, CI, staging, production rollout, and multiple agent sessions. Product intent should not depend on chat history or a single PR description.

For substantial features, keep durable intent under:

```text
specs/<feature-id>/
  spec.md
  plan.md
  tasks.md
  checklists/
```

These artifacts answer different questions:

- `spec.md`: what observable behavior is required and why;
- `plan.md`: how the repository will implement it;
- `tasks.md`: what concrete work remains;
- `checklists/`: requirement-quality or release-readiness checks.

## Routing

Use `.agents/skills/vishar-feature-development/SKILL.md` to classify work.

Do not use the full specification workflow for small fixes by default. Use it for new capabilities, architecture changes, trust-boundary changes, multi-layer work, multi-PR work, or work expected to survive across sessions.

## Workflow

Preferred substantial-feature sequence:

```text
speckit-specify
  -> speckit-clarify (when needed)
  -> speckit-plan
  -> speckit-tasks
  -> speckit-analyze
  -> Vishar exact-head/navigation procedures
  -> speckit-implement
  -> exact-head tests/CI
  -> speckit-converge
```

Repeat implementation and convergence until the remaining work is explicit and either complete or intentionally deferred.

## Important separation of concerns

Spec Kit does not manage Vishar branch topology or production rollout.

Existing repository rules remain authoritative for:

- stacked PRs and exact-head checkout;
- code navigation and RPC/migration tracing;
- authorization and security analysis;
- CI evidence;
- Supabase migration application;
- Cloudflare deployment;
- provider credentials and external account mutation;
- production verification.

A completed `tasks.md` does not prove that production is deployed or healthy.

## Feature directory naming

Use a stable descriptive directory under `specs/`. Prefer an existing issue/feature identifier when one already exists. Otherwise use a short lowercase kebab-case name, for example:

```text
specs/lead-magnet/
specs/artist-self-service-onboarding/
specs/unified-messaging/
```

Do not create a new feature directory for a small bug fix unless the fix belongs to an existing substantial feature spec.

## Artifact ownership

A feature spec is durable project documentation, not disposable agent scratch space.

When implementation reveals a valid requirement change, update the spec and plan deliberately. Do not silently change code away from the specification and then declare the spec stale.

When the current code or a newer ADR disproves an assumption in the feature artifacts, record the conflict and reconcile the artifacts before high-risk work continues.

## Upstream upgrades

The local workflow is based on Spec Kit v1.0.0 semantics, but the Vishar skills are deliberately adapted rather than blindly generated by `specify init`.

Before adopting a newer upstream version:

1. review the upstream changelog;
2. compare command semantics and artifact structure;
3. preserve Vishar constitution and deployment boundaries;
4. update the local skills in a bounded PR;
5. validate that small-task routing still avoids unnecessary ceremony.
